# 「水印天敌」Android 客户端架构说明

## 一、项目定位

一款把图片 / 视频 / PDF / Word / PPT 上传到云端做 AI 去水印的工具类 App，处理完把结果回落到本地相册或下载目录。

客户端不承担任何算法，只负责四件事：**选材 → 上传 → 进度回显 → 结果落地**。算法与计费全部在后端（FastAPI），客户端是薄壳。这套 API 同时供鸿蒙版、iOS 版使用，客户端只换 UI 层。

- 包名：`com.wuyong.allclear`，minSdk 24 / targetSdk 36，竖屏，1.0.0
- 规模：14 个 Kotlin 源文件，约 2800 行

## 二、技术栈

| 层 | 选型 |
| --- | --- |
| 语言 / 构建 | Kotlin 2.2.20、AGP 8.13.2、Gradle Version Catalog |
| UI | Jetpack Compose + Material 3（BOM 2025.09.01） |
| 状态 | AndroidViewModel + `mutableStateOf` / `mutableStateListOf` |
| 网络 | OkHttp 4.12 + `org.json`（手写序列化） |
| 图片加载 | Coil 2.7 |
| 二维码 | ZXing core 3.5.3（纯本地生成，不联网） |
| 持久化 | SharedPreferences（token / 用户缓存 / 隐私同意标记） |

**刻意没有引入的东西**：Retrofit、Moshi/kotlinx.serialization、Hilt/Koin、Room、Navigation-Compose、Paging。
理由见第六节。

## 三、工程结构

单模块 `:app`，按职责分包，不按「功能模块」切：

```
app/src/main/java/com/wuyong/allclear/
├── MainActivity.kt            单 Activity 入口，Scaffold + 底部两 Tab
├── data/                      数据与平台能力
│   ├── Api.kt                 接口地址常量 + 结果 URL 归一化
│   ├── ApiClient.kt           OkHttp 封装：鉴权头、错误码映射、multipart
│   ├── FileProgressBody.kt    自定义 RequestBody：边写边回报上传进度
│   ├── MediaSaver.kt          下载结果 → 相册 / 下载目录（MediaStore 适配）
│   └── UserInfo.kt            用户模型 + 手写 JSON 编解码
└── ui/                        视图与状态
    ├── MainViewModel.kt       唯一的状态持有者（登录态、选材、进度、结果、Toast）
    ├── Theme.kt               设计令牌（AcColor）+ BlueHeader / CardBox 等复用组件
    ├── HomeScreen.kt          去水印主页
    ├── MineScreen.kt          我的页
    ├── RechargeDialog.kt      充值弹窗 + 订单轮询 + 二维码
    ├── Dialogs.kt             登录 / 客服 / 注销 / 协议正文
    ├── PrivacyConsentDialog.kt 首启隐私强确认
    └── ToastHost.kt           全局轻提示
```

## 四、分层与数据流

两层 UI + 一个状态中枢，单向数据流：

```
Composable (无状态渲染)
      ↑ 读 State            ↓ 调方法
MainViewModel (唯一的 State 持有者)
      ↓ 挂起函数
ApiClient / MediaSaver / SharedPreferences
      ↓
HTTPS → FastAPI 后端
```

一次完整链路的时序：

1. `PhotosPicker` / `ActivityResultContracts.PickMultipleVisualMedia` 拿到 `Uri`
2. `MainViewModel.addImages()` 在 IO 线程把 `Uri` 拷进 `cacheDir`（同时做类型识别、体积校验、数量上限校验）
3. 用户点「立即去除」→ `process()` 先做额度预检，剩余次数不足则截断待处理列表
4. 逐个文件 → `ApiClient.removeMedia()`（multipart + `FileProgressBody`）→ 进度回调写进 `progress`
5. 结果 URL 追加到 `results`，`HomeScreen` 自动重组出结果卡片
6. 保存时 `MediaSaver` 下载到缓存 → MediaStore 落库；分享时 FileProvider 出 `content://` 再 `ACTION_SEND`

ViewModel 里没有直接持有 `Context`，用的是 `AndroidViewModel` 的 `getApplication()`，避免 Activity 泄漏。

## 五、几个值得展开的实现点

### 1. 上传进度：自定义 RequestBody

OkHttp 默认的 `RequestBody` 没法回报进度，所以写了一个 `FileProgressBody`：

- 覆写 `contentLength()` 返回 `file.length()`，让服务端能算出总大小
- `writeTo(BufferedSink)` 里用 32KB 的 buffer 循环读文件、写进 sink，每写完一块就回调 `uploaded * 100 / total`
- 关键收益：**全程不把整个文件读进内存**，50MB 的视频也只占 32KB 缓冲

### 2. 超时与长任务

视频/文档是同步处理，服务端可能要跑几分钟。OkHttp 的 `readTimeout` 默认 10 秒会直接崩，所以统一设为 **10 分钟**（connect 20 秒）。同时进度回调让用户知道还在跑，而不是干等。

### 3. 存储适配：MediaStore 事务式写入

- Android 10（API 29）及以上：走 `MediaStore`，**不需要任何存储权限**。写入时先 `IS_PENDING = 1` 占位，写完再置 0 —— 这样相册里不会出现半张图，也不会被其他 App 读到残缺文件
- Android 9 及以下：走公共目录 + `WRITE_EXTERNAL_STORAGE`，manifest 里用 `maxSdkVersion="28"` 限定，高版本系统不会误申请
- 图片落 `Pictures/AllClear`、视频落 `Movies/AllClear`、文档落 `Downloads/AllClear`

### 4. 隐私合规不可绕过

首启弹窗用 `DialogProperties(dismissOnBackPress = false, dismissOnClickOutside = false)`，返回键和点外部都关不掉，必须勾选后点「同意并继续」；不同意则直接 `finish()`。同意状态落 SharedPreferences，只弹一次。

### 5. 审核模式开关

后端 `/system/config` 返回 `in_review`，为 true 时客户端隐藏「充值/升级会员」入口。这样同一份包可以在应用市场审核期隐藏付费入口、过审后再打开。网络异常时**保持上次成功读取的值**，不会因为一次请求失败就误把充值入口放出来。

### 6. 额度扣减与失败返还

处理前按剩余次数截断列表（剩余 3 次、选了 5 个 → 只处理 3 个并提示）；单个文件失败不计次，最后统一 Toast「N 个成功，M 个失败，失败次数不扣除」，收尾再 `refreshUser()` 拉一次真实余额，避免前后端不一致。

### 7. 分享

`FileProvider` 授权 `content://` URI，`ACTION_SEND` + `FLAG_GRANT_READ_URI_PERMISSION`，按类型给 mime（video/mp4、image/*、*/*），交给系统选择器。

### 8. 二维码支付

下单接口只返回 `pay_url`，客户端用 ZXing 在本地把 URL 渲染成二维码（512×512 bitmap），同时提供「打开支付 App」的兜底跳转；下单后每 3 秒轮询一次订单状态，最多 100 次，`paid` 就刷新用户余额并关闭弹窗。

## 六、取舍说明

- **不用 Retrofit**：接口一共 14 个，`OkHttp + JSONObject` 已经够用，省掉 Retrofit + 序列化转换器两层依赖，也省掉注解处理器的编译时间。代价是失去类型安全，见第七节。
- **不用 Navigation-Compose**：只有两个 Tab 加若干 Dialog，一个 `enum Tab` 就够了。引入导航图反而是过度设计。
- **不用 Hilt**：单模块、单 ViewModel，依赖注入框架带来的收益小于它的样板成本。
- **不用 Room**：本地唯一的持久化需求是 token 和一个用户 JSON，SharedPreferences 足够。
- **单 ViewModel**：所有状态集中，跨页面（主页 ↔ 我的页）读余额、登录态不需要额外的事件总线。

## 七、已知不足与改进方向

1. **ViewModel 偏胖**：`MainViewModel` 现在 440 行，同时管登录、选材、上传、结果。页面一多就该按 Screen 拆成 `HomeViewModel` / `MineViewModel` + 共享的 `SessionRepository`。
2. **手写 JSON 无类型安全**：字段改名只能靠运行时发现，换成 `kotlinx.serialization` 或 Moshi 更稳。
3. **缺 Repository 层**：VM 直接依赖 `ApiClient` 单例，不好写单元测试。抽一层 `interface WatermarkRepository` 就能用 fake 实现做纯 JVM 测试。
4. **无断点续传 / 分片**：大视频是全量上传，弱网下中断要重来。可以上分片 + 秒传。
5. **`build.gradle.kts` 里 `isMinifyEnabled = false`**：Release 包没开 R8，体积和反编译防护都有损失。

## 八、一句话总结

一个**用最少的依赖把业务跑通**的 Compose 客户端：单 Activity、单 ViewModel、手写网络层，把复杂度都花在真正难的地方 —— 上传进度、存储权限适配、长耗时任务的用户体验，以及应用市场审核的合规开关上。
